# ADR-001: Use Azure AI Search for RAG retrieval instead of a self-hosted vector database

## Context

The copilot needs a retrieval layer over the knowledge base: given a customer query, find the most relevant KB passages to ground the generated answer (architecture principle P2). Candidates considered were a self-hosted open-source vector database (e.g. running on AKS), and Azure AI Search's built-in vector + hybrid search capability.

Requirements driving this decision: FR-001 (retrieve top-k relevant passages), FR-006 (re-index within 15 minutes of publish), NFR-004 (data stays within the contracted Azure region), and architecture principle P4 (prefer managed Azure PaaS).

## Decision

Use **Azure AI Search** with vector + hybrid (vector + keyword) search over the knowledge-base index, rather than standing up and operating a self-hosted vector database.

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Self-hosted vector DB on AKS | Full control over indexing algorithm; potentially lower per-query cost at very large scale | Team must operate, patch, and scale a stateful cluster; no built-in hybrid search; slower to reach the 15-minute re-index SLA without custom engineering |
| Azure AI Search (chosen) | Managed scaling and availability; native hybrid (vector + keyword) search improves recall over vector-only; integrates directly with Azure OpenAI embeddings; region-pinned to satisfy NFR-004; no infrastructure to operate | Less low-level control over index internals; cost scales with index size and replica count |
| Third-party managed vector DB (outside Azure) | Feature-rich, popular in the RAG ecosystem | Introduces a second cloud vendor and a cross-cloud data-residency question, conflicting with NFR-004 and adding operational surface area for a two-person platform team |

## Consequences

**Positive:**
- No infrastructure operations burden for the platform team — consistent with P4.
- Hybrid search materially improves retrieval recall for exact-match terms (error codes, feature names) that pure vector search sometimes misses.
- Data residency is straightforward to satisfy since the index lives in the same Azure region as other project resources.

**Negative:**
- Ties retrieval infrastructure to Azure; a future multi-cloud strategy would need to revisit this decision.
- Per-query and per-GB indexed cost needs monitoring as the knowledge base and query volume grow (tracked via NFR-009's cost dashboard).

**Follow-up:** Re-evaluate at the 3x-volume mark (NFR-006) to confirm Standard tier replica/partition scaling remains cost-effective versus Azure AI Search's higher tiers.

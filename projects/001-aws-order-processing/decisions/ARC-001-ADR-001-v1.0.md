# ADR-001: Use SQS + Lambda over Kinesis for order-event ingestion

| Field | Value |
|---|---|
| Document ID | `ARC-001-ADR-001-v1.0` |
| Status | Accepted |
| Version | 1.0 |
| Date | 2026-09-17 |
| Author | ArcKit AI Assistant (reviewed by Harish Subash) |

## Context

Orders submitted via `POST /orders` must be buffered between the synchronous API layer and the asynchronous processing that persists them and publishes domain events. Two AWS options were considered for this buffer: **Amazon SQS** (a message queue) and **Amazon Kinesis Data Streams** (an ordered, replayable log). The order-acceptance Lambda must hand off within NFR-001's 800ms p99 budget, and the system must absorb bursts of up to 10x baseline (NFR-002) without losing or duplicating orders beyond what idempotency (NFR-003) already handles.

## Decision

We will use an **SQS standard queue** with a Lambda consumer (`Order Processor`) to buffer and process order-intake messages, with a dead-letter queue for messages that fail repeatedly.

## Alternatives Considered

| Option | Description | Verdict |
|---|---|---|
| **Kinesis Data Streams** | Ordered, replayable stream; consumers track position via shard iterators. | Rejected — strict per-shard ordering is not required (each order is independent; ordering is only needed *within* an order's own event history, which DynamoDB conditional writes already guarantee); shard management and scaling adds operational overhead SQS avoids entirely. |
| **SQS FIFO queue** | Guarantees ordering and exactly-once processing within a message group. | Rejected — FIFO throughput (up to 3,000 msg/sec with batching) is more than sufficient for this workload, but the per-`orderId` message-group model adds complexity with no benefit, since orders are independent of each other. Standard queue's higher throughput ceiling gives more headroom for RISK-01-style burst scenarios. |
| **SQS standard queue** (chosen) | At-least-once delivery, near-unlimited throughput, native Lambda integration, built-in DLQ. | Accepted. |

## Consequences

**Positive:**
- Near-zero operational overhead — no shard capacity planning, no consumer rebalancing logic.
- Native Lambda event-source mapping auto-scales the consumer with queue depth.
- Built-in dead-letter queue directly satisfies Principle P7 (failure is designed for).

**Negative:**
- At-least-once delivery means duplicate messages are possible; this is accepted and handled by the idempotent DynamoDB write in the Order Processor Lambda (Principle P3), not by the queue itself.
- No built-in message replay for analytics use cases — mitigated by the separate EventBridge-to-S3 archive (see `ARC-001-PLAT-v1.0`), which is the correct tool for that job.
- No strict cross-order ordering guarantee — accepted, since no requirement depends on it.

## Status

Accepted 2026-09-17. Superseding this decision would require a new ADR demonstrating a workload change (e.g. a future requirement for strict global event ordering) that SQS cannot satisfy.

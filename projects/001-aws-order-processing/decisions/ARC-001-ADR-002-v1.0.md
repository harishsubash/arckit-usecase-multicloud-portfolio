# ADR-002: Use DynamoDB single-table design over relational RDS for order state

|---|---|

## Context

The platform needs a system of record for order state (order header, line items, status transitions) that supports two access patterns: (1) single-order lookups and writes at high volume during checkout and fulfillment, keyed by `orderId`; and (2) the Customer Support timeline query (FR-007), which retrieves an ordered history of everything that happened to one order. The current monolith uses SQL Server (Amazon RDS-compatible) with a normalised schema across 6 tables and several joins for the equivalent query. Two options were evaluated: staying relational on Amazon RDS, or moving to Amazon DynamoDB with a single-table design.

## Decision

We will use **Amazon DynamoDB** with a single-table design per bounded context. The Orders table uses `orderId` as the partition key and a composite sort key (`eventType#timestamp` or `METADATA`) so that a single `Query` returns both the order header and its full event timeline in one round trip, pre-sorted.

## Alternatives Considered

| Option | Description | Verdict |
|---|---|---|
| **Amazon RDS (SQL Server or PostgreSQL)** | Relational schema, joins for related data, familiar to the current team. | Rejected as the primary store — requires provisioned/reserved capacity that sits idle 10 months of the year (conflicts with Principle P4); connection-pool exhaustion under Lambda's high-concurrency invocation model is a well-known failure mode; the timeline query would require joining 3+ tables. |
| **DynamoDB, one table per entity type** (Orders, OrderEvents, OrderItems) | More conventional DynamoDB modelling, closer to relational mental model. | Rejected — the timeline query (FR-007) would need multiple round trips or a secondary index maintained across tables; single-table design collapses this to one `Query` call, which matters for the support-tooling latency target. |
| **DynamoDB single-table design** (chosen) | One table, partition key `orderId`, sort key encodes record type and time. | Accepted. |

## Consequences

**Positive:**
- On-demand capacity mode means zero idle cost outside peak season, directly supporting the financial case in `ARC-001-SOBC-v1.0`.
- Single-digit-millisecond reads at any scale, with no connection-pool management from Lambda.
- The order-timeline API (FR-007) is a single `Query` operation — no joins, no fan-out reads.
- Conditional writes (`ConditionExpression: attribute_not_exists(orderId)`) give idempotency (Principle P3, NFR-003) for free at the storage layer.

**Negative:**
- Query flexibility is lower than SQL — new access patterns not anticipated at design time may require a new Global Secondary Index or a data-model change, rather than an ad-hoc `WHERE` clause. This is mitigated by keeping the access-pattern list in this ADR's context section current as new requirements emerge.
- The team has less operational experience with DynamoDB capacity/index design than with SQL Server; mitigated by the observability guardrails in Principle P6 and a design review with an AWS Solutions Architect before Beta.
- Ad-hoc reporting/analytics queries (e.g. "total orders by region last quarter") are not efficient against DynamoDB directly — these are served from the S3 event archive (`ARC-001-PLAT-v1.0`) via Athena, not from the live table.

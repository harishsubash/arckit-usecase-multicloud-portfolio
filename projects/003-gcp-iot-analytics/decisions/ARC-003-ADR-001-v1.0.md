# ADR-001: Use Pub/Sub + Dataflow over self-managed Kafka + Flink for telemetry ingestion

## Context

The platform needs a durable, high-throughput ingestion layer for vehicle telemetry (≈1,200 vehicles × 1 message per 10 seconds at full fleet scale) plus a stream-processing layer capable of windowed aggregation, deduplication, and late-data handling (`ARC-003-REQ-v1.0` FR-001–FR-002, NFR-003). Two broad approaches were evaluated: a self-managed open-source stack (Kafka for transport, Flink or Spark Structured Streaming for processing, run on GKE), and GCP's managed equivalents (Pub/Sub for transport, Dataflow/Apache Beam for processing).

## Decision

Use **Pub/Sub** for telemetry ingestion and **Dataflow** (Apache Beam) for stream processing.

## Alternatives Considered

| Option | Assessment |
|---|---|
| Kafka + Flink on GKE (self-managed) | Gives finer control over partitioning and processing semantics, and avoids per-message cloud pricing at very high volumes. Rejected for this workload: requires the Data & Analytics team (4 people) to operate a stateful distributed system 24/7, including upgrades, rebalancing, and capacity planning — capability the team does not currently have, and building it is not a good use of a small team's time relative to the fleet's actual message volume (well within Pub/Sub/Dataflow's comfortable operating range). |
| Kafka (managed, e.g. Confluent Cloud) + Dataflow | A middle ground, keeping Kafka's API surface with managed operations. Rejected: adds a second vendor relationship and a cross-cloud network hop for no functional benefit at this volume, when Pub/Sub meets every ingestion requirement natively within the existing GCP estate. |
| Pub/Sub + Dataflow (chosen) | Meets FR-001/FR-002/NFR-003 out of the box; autoscales without a dedicated ops function; integrates natively with BigQuery/Bigtable sinks used elsewhere in the design; consistent with Principle P4. |

## Consequences

**Positive:**
- No cluster operations burden on the Data & Analytics team; autoscaling handles shift-change spikes (NFR-004) without manual capacity planning.
- Native, low-friction integration with BigQuery and Bigtable sinks used throughout `ARC-003-PLAT-v1.0`.
- Faster time to a working pilot depot (`ARC-003-STRAT-v1.0` Phase 0/1).

**Negative / accepted trade-offs:**
- Ongoing usage-based cost rather than amortised infrastructure cost — accepted and bounded via the cost ceiling in NFR-005 and Principle P5.
- Some lock-in to GCP-specific APIs (Pub/Sub, Dataflow) — accepted, consistent with Principle P4's preference for managed services, and the fleet telemetry domain does not require multi-cloud portability.

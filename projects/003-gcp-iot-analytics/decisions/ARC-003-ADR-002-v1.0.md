# ADR-002: Use Bigtable for current-vehicle-state serving over querying BigQuery directly

| Field | Value |
|---|---|
| Document ID | `ARC-003-ADR-002-v1.0` |
| Status | Accepted |

| Date | 2026-09-17 |
| Author | ArcKit AI Assistant (reviewed by Harish Subash) |

## Context

Fleet Operations needs a "where is vehicle X right now" lookup with p99 latency under 100ms (`ARC-003-REQ-v1.0` FR-005), used by both the internal operations API and the geofence alert evaluator. BigQuery is the platform's analytical system of record (Principle P2) but, as a columnar analytical warehouse, is not designed for high-frequency, low-latency single-row point lookups at this latency bound.

## Decision

Serve current-vehicle-state lookups from **Bigtable**, populated as a fan-out sink from the same Dataflow pipeline that writes to BigQuery — not as an independent write path.

## Alternatives Considered

| Option | Assessment |
|---|---|
| Query BigQuery directly for current state | Simplest architecture (one fewer component). Rejected: BigQuery query latency (typically hundreds of ms to seconds, even for small scans) cannot reliably meet the sub-100ms p99 requirement, and running frequent point-lookup queries against an analytical warehouse works against its cost/query model (Principle P5) — a lookup used by an alerting hot path would itself become a source of unnecessary BigQuery spend. |
| Firestore | A viable low-latency NoSQL option. Rejected in favour of Bigtable primarily for consistency with the team's existing GCP data-engineering skill set and Dataflow's native Bigtable I/O connector, which simplifies the fan-out sink; at 1,200 rows the choice is not scale-driven, so the deciding factor was pipeline integration simplicity rather than a hard technical requirement. This is a low-stakes choice and could be revisited without disruption if requirements change. |
| In-memory cache (e.g. Memorystore/Redis) in front of BigQuery | Would meet latency but introduces a cache-invalidation problem and a second system to keep consistent with the canonical pipeline. Rejected as unnecessary complexity: Bigtable, written directly by Dataflow, avoids the invalidation problem entirely by being the write target itself, not a cache in front of one. |

## Consequences

**Positive:**
- Meets FR-005's p99 < 100ms requirement directly.
- Because Bigtable is written by the same Dataflow job as BigQuery (Principle P2), there is no second independent write path and therefore no risk of the two stores drifting apart.
- Simple, predictable cost profile at fleet scale (1,200 rows), independent of query volume.

**Negative / accepted trade-offs:**
- Introduces a second storage technology to operate and monitor, alongside BigQuery — accepted, since it directly serves a requirement BigQuery cannot meet, and Dataflow's native connector keeps operational overhead low.
- Bigtable is schema-flexible but requires care with row-key design; a single `vehicle_id`-keyed table is simple enough at this scale that this risk is low.
